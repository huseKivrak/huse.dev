claude flywheel

a failure-driven improvement loop for our Claude Code setup. incidents in, reviewed convention fixes out, lessons compounding.

the problem

Everyone on the team runs Claude Code against the same committed config: CLAUDE.md, .claude/skills, .claude/rules, .claude/commands. Call that the harness. Today the harness only improves when one of us personally notices a failure, diagnoses it, and edits a file. Which means:

1. the same failure bites you, then me, then Daniel, because a lesson learned in one head never reaches the repo
2. conventions get deleted or duplicated with no record of why they existed, so every cleanup re-argues settled questions
3. "why is this rule here" is unanswerable a month later
4. nobody can tell whether a config edit helped, hurt, or did nothing

the loop

1 · anyone, any session
/flywheel-report
Claude misbehaves > you run one command in that session. It writes a sanitized record (symptom, behavior, mechanism), never chat logs. Under a minute or it doesn't count.
2 · shared queue
intake
Singleton reports wait here. One occurrence is noise; when a second dev hits the same mechanism, it's a pattern.
3 · steward, ~weekly
/flywheel-retro
Clusters reports by root cause, checks the graveyard, drafts the narrowest fix that kills the mechanism. Deletions get adversarially refuted first.
4 · the only gate
normal PR review
Every fix ships as an ordinary PR with the evidence linked. No bots, no self-merge, no new process. You review it like anything else.

↩ merged fix updates the harness > that failure stops recurring > the ledger proves it (or proves it didn't)

the two files that do the real work

a
failures.md (blameless incident DB)
Every recurring failure pattern, recorded at three levels: what you saw, what Claude did, why it happens. Doubles as the "known Claude gotchas in this repo" doc, which is the onboarding page we never wrote.
b
rejections.md (the graveyard)
Every idea we tried or considered and killed, with the evidence that killed it. Next time anyone says "why don't we just delete X", the answer is a link instead of a thread. Dead ideas stay dead.

rules of the game

1
mechanism over symptom
Two incidents cluster only if they fail the same way for the same reason. Same symptom, different cause = different patterns.
2
patterns, not incidents
2+ occurrences before any fix is proposed. One bad session is weather, not climate.
3
refute before deleting
Measured in the lab: ~30% of "obviously safe to delete" convention cuts were wrong. So every deletion faces a skeptic agent whose only job is to prove it's load-bearing. Additions are cheap; deletions are guilty until proven innocent.
4
falsifiable edits
Every fix states what observable behavior should stop, and what might break. The next retro checks the prediction. Edits that can't be checked don't get made.
5
the evaluator sits outside the loop
The things that verify quality (settings, hooks, build anchors, eventually an eval suite) are never edited by any flywheel workflow. An optimizer that can edit its own grader will eventually "improve" by deleting it.
6
nothing is autonomous
Nothing runs unattended, nothing self-merges, no transcripts leave anyone's machine. A human runs it; humans review everything.

receipts (real patterns from the prototype)

I've been running the full apparatus privately as a lab. It has already caught, among others:

trial-merge misread · ADO populates lastMergeCommit on Active PRs with trial-merge simulations, so "merged" got written for open PRs. fixed: verify against origin/master before claiming merged, documented in the ADO skill.
compound-AC atom drops · "X by default / else Y" acceptance criteria silently lose the else-clause under paraphrase, and typecheck can't see it. fixed: review procedure now splits every AC into atoms and verifies each one.
five migration folders · searches hit API/migrations/ only; backfills live in migrations-after/, so real files got reported as absent. fixed: folder set documented, glob widened.
confident fabrication · claims arrived with sources attached ("the manual confirms", "this memory rule says") that were never checked and turned out false. fixed: policy line, plus an eval task where a fresh git repo makes any confident blame-claim a fabrication by construction.

In its first full cycle the skeptic agents killed 2 of 5 proposed fixes before they shipped; one of them would have re-made an edit that had already been made and reverted the same day. The graveyard works.

what's in it for you, specifically

1. When Claude does something dumb in your session, you get a <1-minute way to make it someone's problem (mine) instead of just being annoyed.

2. The report command doubles as instant lookup: if your issue matches a known pattern, it tells you the documented workaround on the spot.

3. The graveyard means your review objections become permanent. Kill a bad idea once in a PR thread and it stays killed, with your evidence attached.

4. Zero process tax: no meetings, no forms, no bot spam. If you never run the command, the only thing you see is the occasional small, evidence-linked Dev Tooling PR.

honesty corner: the failure mode of this whole genre is ceremony — building an apparatus a solo operator IS. The prototype deliberately over-built everything to find that line (it has a written verdict on which parts are theater). The shared version ships only the parts that survived: two files, two commands, and the review process we already have. Everything fancier has to earn its way in with a logged failure it would have prevented. If after a quarter nobody but me feeds it, we archive it and I'll admit it on this page.
